Apache Ignite (T6)

Anti-patrón

Ineficiencia

Triple Simulación

FlexCube es invocado 3 veces para construir opciones de cuotas que luego se descartan.

Bloqueante

Sin Omnicanalidad

No es posible iniciar un crédito en un canal y continuarlo en otro. Cada canal es una isla.

Stack EOL

Dependencia

Principios de Diseño de la Nueva Arquitectura

🔁

Omnicanalidad Real

El estado del crédito persiste en sesión centralizada. El afiliado puede iniciar en TAPP, continuar en SVP y finalizar en sucursal.

⚡

Evaluación Única

La preevaluación ES la evaluación formal. Se elimina el Servicio 147 y la doble invocación de "La Araña".

📡

Event-Driven

Kafka como columna vertebral asíncrona. Las cargas de campaña no colapsan el motor de riesgo.

🛡️

Resiliencia

Circuit breakers en todos los servicios. Sin puntos únicos de falla. Degradación graciosa.

📈

Escalabilidad Horizontal

Microservicios en GKE/OKE. Auto-scaling por demanda. Sin dependencia de pools fijos de 4 hilos.

👁️

Observabilidad Total

Prometheus + Grafana + Jaeger. Trazabilidad distribuida. Alertas proactivas antes del impacto al negocio.

Causa Raíz Primaria

T6 CAUSA RAÍZ — CONFIRMADA

Apache Ignite — Kill de Nodos Sanos

Apache Ignite mata nodos sanos por falsos positivos en la detección de fallas (failureDetectionTimeout menor que metricsUpdateFrequency). Con 0 backups configurados, cada kill genera pérdida total de caché y cascada de errores. El agente APM genera el 12.57% del tráfico HTTP total y el 79.9% de los errores. ARIs: ARI-14, 15, 16, 52, 53, 54, 55, 56, 57.

Hallazgos de Arquitectura

FG-22Crítico

Doble Invocación (Servicio 147)

Al confirmar el crédito, el Servicio 147 re-ejecuta toda "La Araña": MenuAndes, FlexCube, Experian, BigQuery y Blaze. El trabajo de la preevaluación se descarta por completo.

+4s latencia2× carga motorAnti-patrón
FG-26Crítico

Triple Simulación FlexCube

Para mostrar opciones de pago (24, 36, 48 cuotas), el sistema invoca 3 veces al core bancario generando cuadros completos que luego se descartan. El simulador express no se usa por diferencias de $1-$2 en redondeo.

3× carga FlexCubeRedondeo bloquea mejora
FG-19Alto

BigQuery Síncrono — 4.3s de Latencia

El Scoring Middleware conecta OCI con GCP de forma síncrona. Cada evaluación espera ~4.3 segundos la respuesta de BigQuery. Las variables de riesgo se actualizan solo mensualmente (batch).

~4,312ms / llamadaVariables mensuales
FG-05Alto

OSB sin Circuit Breakers

El Oracle Service Bus no tiene circuit breakers en ninguno de sus 14 servicios. Cuando se satura, los hilos se agotan y hasta 13 servicios caen en cascada simultáneamente. Timeout configurado en 50 segundos.

50s timeout13 servicios en cascada
FG-12Alto

Datos Desincronizados (T5)

Los datos de MenuAndes se sincronizan con Siebel por procesos batch nocturnos. Las inconsistencias generan excepciones Nashorn que alimentan el Full GC del motor FICO. EAI-005 registró 18.350 errores en 5 meses.

18,350 errores EAI-005Sync nocturno
FG-25Alto

Baja Base Aprobados Fallida

El microservicio de baja en TAPP falla regularmente. El sistema depende de un proceso batch nocturno para registrar que un crédito ya fue otorgado, lo que permite re-solicitudes indebidas el mismo día.

Re-solicitudes indebidasBatch nocturno

Omnicanalidad — ¿Cómo funciona?

💡 La clave es que el estado del crédito se almacena en Redis indexado por RUT. Cada paso del flujo escribe su resultado en la sesión. Cualquier canal que autentique al mismo afiliado puede leer y continuar desde donde quedó.

🟢 Inicio en TAPP

El afiliado inicia la solicitud en la app móvil. Pasa la evaluación. Se interrumpe antes de firmar.

→ Estado guardado en Redis

🔵 Continuación en SVP

Al día siguiente entra desde la Sucursal Virtual. El sistema detecta una sesión activa y carga el crédito pendiente de firma.

→ No re-evalúa si el resultado aún es válido

🟡 Cierre Presencial

Si necesita apoyo, el ejecutivo en Salesforce ve el mismo estado del crédito y puede completar la operación sin empezar desde cero.

→ Desembolso unificado vía Toku/Redbanc

Credit Orchestrator — Camel + Redis

Implementación del orquestador de crédito con Apache Camel como motor de rutas y Redis como máquina de estados

Comparativa de Modelos Arquitectónicos

Modelo 1 — el diseño original de esta presentación (microservicios independientes, orquestación distribuida). Modelo 2 — Camel + Redis como eje central.

CRITERIO MODELO 1 — Microservicios + Temporal / Kong MODELO 2 — Apache Camel + Redis

🟢 Ventaja  ·  🟡 Neutral / posible  ·  🔴 Desventaja

⚖️
Recomendación para Caja Los Andes: El Modelo 2 (Camel + Redis) es la opción más pragmática en este contexto. Resuelve dos problemas con una sola herramienta: reemplaza el OSB y orquesta el crédito. No requiere infraestructura nueva, el equipo ya conoce Java, y Redis existe en producción. El Modelo 1 es arquitectónicamente más puro y escala mejor a largo plazo, pero implica mayor costo inicial, más piezas independientes y una curva de aprendizaje con Temporal que no está justificada en el horizonte 2026.

Arquitectura del Orquestador

Camel corre en OKE como microservicio Spring Boot. Redis gestiona el estado del crédito. Kafka conecta los eventos entre rutas.

Sinergias con el modelo Camel + Redis

Migración OSB

Camel reemplaza el OSB gradualmente

La misma instancia de Camel que orquesta el crédito puede asumir las rutas del OSB una a una. EAI-005 (FlexCube), EAI-053/106/110 (MenuAndes) se migran como rutas Camel sin levantar nueva infraestructura. El retiro del OSB en Q3 2026 se convierte en una transición progresiva, no un big bang.

Circuit Breakers

Resilience4j en todas las rutas

Camel integra Resilience4j nativamente. Cada ruta hacia FlexCube, MenuAndes y FICO tiene su propio circuit breaker, retry con backoff exponencial y fallback. Se resuelve el problema de cascada del OSB sin circuit breakers que hoy baja 13 servicios simultáneamente.

Observabilidad

Métricas Camel → Prometheus/Grafana

Camel expone métricas por ruta vía Micrometer: tiempo de ejecución, tasa de error, throughput. Se integran directamente en el dashboard de Grafana existente. Cada ruta tiene su propio SLA medible sin instrumentación adicional.

Camel K

Deploy nativo en OKE

Camel K corre directamente sobre Kubernetes/OKE — el mismo cluster donde está FICO v7. Cada ruta se despliega como un operador independiente: se puede actualizar la ruta de desembolso sin tocar la de evaluación. Auto-scaling por ruta según demanda.

Redis existente

Sin infraestructura nueva

Redis ya existe en el ecosistema (caché de preevaluación). El state store del Credit Orchestrator se agrega como un nuevo keyspace en el mismo cluster. La operación de Redis ya es conocida por el equipo — cero curva de aprendizaje de plataforma.

Dead Letter Channel

Compensación con patrón Camel nativo

Camel tiene el patrón Dead Letter Channel integrado. Si una ruta falla después de los reintentos, el mensaje se envía a un topic Kafka de errores y se actualiza el estado en Redis a COMPENSATING. El equipo puede reintentar manualmente o escalar a soporte sin perder el contexto del crédito.

Ejemplo de Ruta — Formalización sin doble invocación

// Ruta: formalization — reemplaza el Servicio 147
// Lee el resultado de la preevaluación desde Redis
// sin llamar a FICO por segunda vez

from("kafka:credit.option.selected?groupId=credit-orchestrator")
  .process(exchange -> {
    String rut = exchange.getIn().getHeader("rut", String.class);

    // 1. Leer estado guardado en Redis (sin re-evaluar)
    CreditSession session = redisService.getSession(rut);
    if (session == null || session.isExpired()) {
      throw new SessionExpiredException("Sesión vencida para RUT: " + rut);
    }

    // 2. Actualizar estado → FORMALIZING
    redisService.setState(rut, CreditState.FORMALIZING);
    exchange.getIn().setBody(session);
  })

  // 3. Crear crédito directamente en FlexCube 14.7 REST
  .circuitBreaker()
    .resilience4jConfiguration()
      .slidingWindowSize(10).failureRateThreshold(50)
      .waitDurationInOpenState(30).end()
    .to("rest:post:flexcube/credit/create")
  .onFallback()
    .process(e -> redisService.setState(e.getIn().getHeader("rut", String.class),
                                             CreditState.COMPENSATING))
  .end()

  // 4. Publicar evento para que Document Service genere PDFs
  .to("kafka:credit.formalized?brokers={{kafka.brokers}}")

  // 5. Estado → DOCS_GENERATED (lo actualiza la ruta de documentos)
  .log("Crédito formalizado sin re-evaluación: ${header.rut}");
